## 1. 知识库、规则库与算法部署

### Q1. 参赛方是否可以包含医学知识库、规则库和本地检索模块？

可以。比赛鼓励采用不同的技术路线，包括但不限于提示词工程、RAG、规则引擎、多阶段推理和 Agent 工作流。

参赛方可以将固定版本的医学知识库、规则库和本地检索模块集成到算法 ZIP 包中，前提是这些资源来源合法、能在指定的比赛环境中独立运行，且不依赖外部在线服务。

### Q2. 知识资源应如何登记？

提交时，须登记每项资源的名称、来源、版本、用途、文件大小以及必要的运行时依赖。

组委会将提供统一的登记模板。未使用额外知识库或规则库的队伍应注明“None”。

### Q3. 算法包大小、Python 依赖和网络访问有哪些限制？

原则上支持合理的第三方 Python 依赖以及本地检索与计算组件。

参赛方须提供完整的依赖说明，例如 `requirements.txt`，并确保其方案能在比赛环境中部署和运行。

算法包大小限制和依赖兼容性要求将在官方评测前统一明确。计划使用大型知识库或特殊依赖的队伍，建议提前联系组委会。

官方评测环境不提供公网访问，仅可调用指定的比赛内部服务。算法在执行期间不得在线安装或下载额外的依赖或资源。

## 2. 模型请求参数与评测资源

### Q4. 是否支持 seed 参数？

比赛使用自托管的 vLLM 模型服务。vLLM 原生支持请求级 seed 参数，可直接在 HTTP JSON 请求体顶层传入，例如 `"seed": 42`。

参赛方可以使用固定随机种子。若实际 API 不支持该字段，参赛方可省略，并在提交说明中说明；此情况不视为违规。

固定种子有助于提升可复现性，但并不保证在不同运行条件下得到完全相同的模型输出。

### Q5. Token、模型调用、超时和重试有哪些限制？

在当前开发与测试阶段，尚未设定明确的总 Token 上限。

官方评测时，主办方将根据共享资源配置确定各项限额，包括单次模型请求的超时、单例总运行时长、Token 消耗量、模型调用次数和重试次数。

原则上，由参赛方算法主动发起的重试计入模型调用预算。经确认受比赛平台自身故障影响的调用，将按统一的异常处理规则处理。

具体限额将在最终提交截止前公布，并为参赛方预留调整方案的时间。

### Q6. 参赛方是否可以配置 response_format 和 temperature？

自托管的 vLLM OpenAI-compatible API 原生支持 temperature，并在受支持的版本中支持通过 response_format 进行结构化输出，例如：

```json
{
  "temperature": 0.1,
  "response_format": {
    "type": "json_object"
  }
}
```

原则上，参赛方可自行配置这些参数。最终支持情况以实际部署的比赛版本和统一的 API 规范为准。

对于禁止或不支持的参数，主办方将尽量给出明确的错误提示，避免因参数被静默忽略而造成误解。

### Q7. Qwen 的 Thinking 参数应如何传入？

对于使用 vLLM 原生 OpenAI-compatible API 的服务，可通过 HTTP 请求体中的以下字段关闭 Thinking：

```json
{
  "chat_template_kwargs": {
    "enable_thinking": false
  }
}
```

若省略该字段，服务将使用其实际的服务端默认配置。该默认配置不一定关闭 Thinking；具体行为由比赛公布的模型配置决定。

原则上，参赛方可按算法策略选择 Thinking 模式。具体支持情况将通过统一的 API 示例予以确认。

## 3. 外部 API 与数据安全

### Q8. 参赛方是否可以使用商用 Qwen API 或其他第三方服务？

比赛禁止使用任何外部第三方 API。

比赛提供统一的自托管 Qwen 模型服务。参赛算法须通过指定的比赛 API 执行模型推理。

禁止调用外部商用大语言模型、在线 Embedding 服务、在线知识检索或其他第三方服务。

比赛提供的练习病例和官方评测病例均不得上传至外部第三方平台。

参赛方可以使用本地知识库、规则库、检索算法和其他离线组件，前提是资源已提前登记，并能在指定的比赛环境中独立运行。

本规则旨在保护数据安全、评测公平性和可复现性。

## 4. 结果提交与兼容性

### Q9. 结果文件应命名为 output.json 还是 results.json？

技术规范和提交材料目前使用的文件名不一致。组委会将统一修订，并明确最终的文件名和数据结构要求。

在兼容性预检中，主办方将尽可能同时兼容现有文档中出现的两种文件名，以免因文档差异影响参赛方测试。

正式提交须遵循更新后的统一技术规范。

## 5. 推理基础设施与运行环境

### Q10. 自托管 vLLM 服务是否使用前缀缓存？参赛方是否必须添加 cachemark？

比赛使用自托管的 vLLM 推理服务。vLLM 原生支持自动前缀缓存；参赛方无需在请求的输入或输出中手动添加任何缓存标记（`cachemark`）。

前缀缓存是否启用及其具体配置由组委会统一管理；参赛方无需自行处理。官方评测计划统一关闭自动前缀缓存，以减少缓存状态对评测过程的影响。最终以公布的环境配置为准。

### Q11. 推理结果的可复现性如何？固定随机种子能保证什么？

主办方理解，浮点计算、并发调度和推理优化可能使大模型推理带有一定程度的不确定性。

比赛将统一模型版本、推理框架、运行环境和评测条件，并允许参赛方在接口支持的范围内设置固定随机种子。

需要说明的是，固定随机种子并不等同于保证模型输出完全一致。比赛主要保证评测条件一致、结果可核验；并不要求每次生成逐字相同。

参赛方只需确保自身代码、依赖和知识资源固定为确定的版本，并合理控制算法内部的随机行为。

### Q12. 参赛方是否可以自行部署 BGE-M3 或其他 Embedding 模型？

考虑到比赛使用华为 Ascend 技术栈，为降低部署复杂度并保证评测公平性，主办方计划提供统一的内网 Embedding API。参赛方可通过该统一接口生成向量，并自行实现知识库构建、向量检索、混合召回等 RAG 算法逻辑。

原则上不支持参赛方自行部署需要 GPU/NPU 资源的 Embedding 模型。允许提交本地知识库和预建索引；具体资源大小限制将统一公布。

### Q13. 企业赛道提供什么硬件？参赛方是否可以运行本地推理？

企业赛道的模型推理统一部署在华为 Ascend 技术栈上。

参赛方算法原则上在隔离 CPU 环境中运行，不直接分配 GPU/NPU 资源。在规定资源限额内，参赛方可运行 Python 程序、规则计算、本地检索及其他轻量计算任务。

参赛方不得部署或运行额外的自托管大模型或 GPU/NPU 推理服务。特殊的 CPU 计算依赖可提前申报，以进行兼容性评估。

具体的操作系统、CPU、内存、存储和运行时限将在官方评测环境说明中统一规定。
