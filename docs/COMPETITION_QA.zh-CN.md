## 一、知识库、规则库及算法部署

### Q1. 是否允许携带医学知识库、规则库和本地检索模块？

允许。赛事鼓励参赛方采用不同的技术路线，包括但不限于 Prompt Engineering、RAG、规则引擎、多阶段推理、Agent 工作流等。

参赛方可将固定版本的医学知识库、规则库及本地检索模块集成到算法 ZIP 中，前提是相关资源来源合法合规，能够在赛事指定环境中独立运行，不依赖外部在线服务。

### Q2. 知识资料如何登记？

请在提交时登记相关资源的名称、来源、版本、用途、文件大小及必要的运行依赖。

具体登记模板由组委会统一提供。未使用额外知识库或规则库的团队，注明“无”即可。

### Q3. 算法包大小、Python 依赖和联网访问有何限制？

原则上支持合理的 Python 第三方依赖及本地检索、计算组件。

参赛方需提供完整依赖说明（如 `requirements.txt`），确保方案能够在赛事环境中部署运行。

算法包大小上限和依赖兼容性要求将在正式评测前统一明确。对于较大的知识库或特殊依赖，建议提前与组委会沟通。

正式评测环境不开放公网访问，仅允许调用赛事指定的内部服务。算法运行期间不得在线下载安装额外依赖或资源。

## 二、模型调用参数及评测资源

### Q4. 是否支持 seed 参数？

赛事采用自部署 vLLM 模型服务。vLLM 原生支持请求级 seed 参数，可直接在 HTTP JSON 请求体顶层传入，例如 `"seed": 42`。

参赛方可使用固定随机种子。若实际接口不支持该字段，允许不传并在提交说明中注明，不因此判定违规。

需要说明的是，固定 seed 有助于提高可复现性，但不代表不同运行条件下模型输出一定完全一致。

### Q5. Token、调用次数、超时和重试限制如何设置？

当前开发测试阶段暂未设置明确的 Token 总量限制。

正式评测阶段将根据统一资源配置，对单次模型请求超时、单病例总运行时长、Token 消耗、模型调用次数及重试次数等进行规范。

原则上，参赛算法主动发起的重试计入模型调用预算；经确认属于赛事平台自身故障的调用，将按统一异常处理规则处理。

具体限制将在正式提交截止前统一发布，并为参赛方预留调整时间。

### Q6. 是否允许设置 response_format 和 temperature？

自部署 vLLM 的 OpenAI 兼容接口原生支持 temperature，并在支持的版本中提供 response_format 结构化输出能力，例如：

```json
{
  "temperature": 0.1,
  "response_format": {
    "type": "json_object"
  }
}
```

赛事原则上允许参赛方自主设置上述参数，最终以赛事实际部署版本及统一接口规范为准。

对于赛事禁止或接口不支持的参数，将尽量提供明确的错误提示，避免静默忽略造成理解偏差。

### Q7. Qwen Thinking 参数如何传递？

对于采用 vLLM 原生 OpenAI 兼容接口的服务，可以通过 HTTP 请求体中的以下字段关闭 Thinking：

```json
{
  "chat_template_kwargs": {
    "enable_thinking": false
  }
}
```

如果不传该字段，则使用服务端实际配置的默认模式。默认模式并不必然是关闭 Thinking，最终以赛事发布的模型配置为准。

赛事原则上允许参赛方根据算法策略选择 Thinking 模式，具体支持情况将通过统一接口示例确认。

## 三、外部 API 与数据安全

### Q8. 能否使用商业 Qwen API 或其他第三方服务？

本次赛事禁止使用任何外部第三方 API。

赛事提供统一的自部署 Qwen 模型服务，参赛算法应通过赛事指定接口完成模型推理。

禁止调用外部商业大模型、在线 Embedding、在线知识检索或其他第三方服务。

赛事提供的练习病例及正式评测病例均不得上传至外部第三方平台。

参赛方可以使用本地知识库、规则库、检索算法及其他离线组件，但相关资源需提前登记，并确保在赛事指定环境中独立运行。

此项规定旨在保障数据安全、评测公平性及结果可复现性。

在兼容性预检阶段，将尽可能兼容已有文档中的两种命名方式，避免因文档差异影响参赛方测试。

## 五、补充答复：推理基础设施与运行环境

### Q10. 关于 vLLM 前缀缓存及 cachemark

赛事采用自部署的 vLLM 推理服务。vLLM 原生支持自动前缀缓存机制，不需要参赛方在请求的 input 或 output 中手动添加 cachemark。

前缀缓存是否启用及具体配置由赛事方统一管理，参赛方无需自行处理。正式评测拟统一关闭自动前缀缓存，以减少缓存状态对评测过程的影响，最终以公布的环境配置为准。

### Q11. 关于推理结果的可复现性

我们理解大模型推理过程中，浮点计算、并发调度及推理优化可能引入一定的非确定性。

赛事将统一模型版本、推理框架、运行环境及评测条件，并允许参赛方在接口支持范围内设置固定随机种子。

需要说明的是，固定随机种子不等于保证模型输出完全一致。赛事主要保证评测条件一致及结果可核验，不要求每次生成结果逐字相同。

参赛方只需确保自身代码、依赖及知识资源版本固定，并合理控制算法内部的随机行为。

### Q12. 关于 BGE-M3 等 Embedding 模型

考虑到赛事采用华为昇腾技术栈，为降低部署复杂度并保证评测公平性，赛事计划统一提供内网 Embedding API。

参赛方可以通过统一接口生成向量，并自行实现知识库构建、向量检索、混合召回及其他 RAG 算法逻辑。

原则上不支持参赛方自行部署需要 GPU/NPU 资源的 Embedding 模型。允许提交本地知识库及预构建索引，具体资源大小限制将统一公布。

### Q13. 关于企业赛硬件与本地推理

企业赛模型推理服务基于华为昇腾技术栈统一部署。

参赛算法原则上运行在隔离的 CPU 环境中，不直接分配 GPU/NPU 资源。

允许在规定资源范围内执行 Python 程序、规则计算、本地检索及其他轻量级计算任务。

不开放参赛方自行部署和运行额外的大模型或 GPU/NPU 推理服务。对于特殊的 CPU 计算依赖，可提前申报并进行兼容性评估。

具体操作系统、CPU、内存、存储及运行时限，将在正式评测环境规范中统一明确。

## 六、补充答复：输出格式与 Embedding 服务（2026-11-20）

以下三条为 2026-11-20 补充答复；Q14-Q16 为项目侧暂记编号，主办方原文未编号。

### Q14. 关于 response_format 支持范围

赛事使用自部署的 vLLM Ascend 推理服务。vLLM 原生支持 `text`、`json_object`、`json_schema` 等输出格式。

原则上支持参赛方使用 `json_schema` 进行结构化输出约束。具体支持的参数范围及 JSON Schema 特性，将以赛事实际部署版本的兼容性验证结果为准，并统一提供参数清单及调用示例。

### Q15. 关于内网 Embedding 的硬件资源评分

赛事统一提供内网 Embedding API，参赛方无需自行部署向量模型。

Embedding 服务的底层 NPU 资源由赛事方统一管理，其显存和算力占用不直接计入参赛方的硬件资源评分。

赛事将对调用次数及使用量进行统一管理，确保不同参赛方案使用相同的资源条件。

### Q16. 关于 Embedding 模型、精度及测试接口

赛事拟统一采用开源 BGE-M3（BAAI/bge-m3）模型，基于华为昇腾 910B 部署。

官方模型权重地址：https://huggingface.co/BAAI/bge-m3

模型主要参数：
- Dense Embedding：1024 维
- 最大模型序列长度：8192 Tokens
- 支持中文及多语言检索
- 同时具备 Dense、Sparse 和 ColBERT 检索能力

推理精度优先采用 FP16，不额外量化，最终以部署验证后的配置为准。

BGE-M3 常规检索不需要额外添加 Instruction。赛事计划首先开放统一的 Dense Embedding 接口，不单独提供 Instruction 参数。

我们将提供低频内网测试接口，采用统一的 HTTP API 调用方式，供参赛方提前测试向量生成、知识库索引构建及 RAG 检索逻辑。

具体接口地址、认证方式、调用示例、配额及最终模型版本将在服务验证完成后统一公布，正式评测期间保持一致。

## 七、厂商答复：模型接口与评测安排（2026-11-24 补充，摘要）

来源：项目负责人提供的《赛题组常见问题咨询》前半部分（厂商侧答复）及项目负责人确认的模型名称。以下为要点摘要，不是原文照录；原文以该文档为准。Q17-Q21 为项目侧临时编号。

### Q17. 指定模型及接口兼容性

官方规定模型名称为 `qwen3.8-27b`。接口基本兼容 OpenAI Chat Completions，messages、temperature、max_tokens、stream、tools 等常规字段与 OpenAI 一致。赛前是否提供与正式评测一致的测试接口及开放时间，由赛事组织方统一安排。

### Q18. Thinking 与流式输出

`qwen3.8-27b` 默认开启 Thinking；不传思考参数即可运行，关闭 Thinking 或调整推理深度时通过扩展参数传入（vLLM 为 `chat_template_kwargs`，见 Q7）。允许选手自行关闭深度思考；开启深度思考时允许使用流式输出。`temperature`、`max_tokens`、`response_format` 支持调节，是否允许队伍自行调整由组织方后台设置（另见 Q6、Q14）。

### Q19. 正式评测病例数量

正式评测数量为 1，所有队伍使用同一份病历。企业赛与总决赛分别提供一份，总决赛难度更高；企业赛病例在比赛开始时随赛程通知下发。评分维度与技术文件见赛题规则附件。

### Q20. Token 与调用限制

Token 限额、调用次数、并发、超时、重试和运行时限属于赛制规则，由组织方在后台设置（正式限额另见 Q5）。

### Q21. 算法与外部知识、配套资料

允许多阶段 Workflow、多智能体协作，以及携带固定版本的医学知识库、规则库和本地检索模块（登记要求见 Q1、Q2）。练习病例、模型清单和接口文档按组委会统一通知发布。厂商答复同时重申：须合规使用，只调用赛方公布的指定模型（与 Q8 一致）。
